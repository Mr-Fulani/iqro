# IQRO Mobile

Нативный мобильный клиент IQRO на Flutter для Android, iPhone и iPad. Все платформы
используют один Dart-код и действующие API-контракты платформы, хранят пользовательские
изменения локально и синхронизируют их после восстановления сети.

## Быстрый запуск на Android

Требуются Flutter 3.41+, Android SDK и устройство с включённой USB-отладкой либо
Android Emulator.

```bash
cd clients/iqro_mobile
flutter pub get
flutter doctor
flutter devices
flutter run \
  --dart-define=API_BASE_URL=https://staging.iqro.forum \
  --dart-define=APP_ENV=staging
```

При первом запуске приложение создаёт безопасную гостевую сессию. Коран, Мусхаф,
чтецы, аудио, ду’а, время намаза и функция «Поделиться» загружаются со staging API.

В разделе «Аудио» карточка с круглым аватаром является основной кнопкой запуска:
тап выбирает доступный вариант чтения, продолжает текущую суру (либо открывает
Аль-Фатиху), запускает воспроизведение и сразу показывает полный плеер. Над сеткой
работает фильтр по виду чтения; по умолчанию выбран «Мурратталь», а недоступные в
каталоге виды не показываются. Несколько стилей одного чтеца остаются одной персоной
в соответствующих фильтрах, поэтому дубли аватаров внутри одного вида не создаются.
Развёрнутый плеер показывает фактический битрейт и позволяет выбрать только опубликованные
для текущего трека варианты `economy`, `standard` или `high`. Выбор хранится на устройстве;
если нужного варианта нет у другой записи, используется назначенный бэкендом default без
ошибки воспроизведения.

В «Настройки → Офлайн-хранилище» перечислены все полные и частично загруженные пакеты,
их фактический размер на устройстве, заявленный полный размер и состояние. До начала загрузки
размер берётся из проверенного manifest и показывается в отдельном подтверждении. Общий лимит
приложения — 3 ГБ; автоматического удаления нет, каждый конкретный пакет удаляется только после
подтверждения. Активная офлайн-запись сначала корректно останавливает плеер.

## Тестовый APK

```bash
flutter build apk --debug \
  --dart-define=API_BASE_URL=https://staging.iqro.forum \
  --dart-define=APP_ENV=staging

adb install -r build/app/outputs/flutter-apk/app-debug.apk
```

- application ID: `forum.iqro.app`;
- минимальная версия Android определяется поддерживаемой версией Flutter;
- staging используется по умолчанию только в debug-режиме;
- release-сборка без явных `APP_ENV` и `API_BASE_URL` намеренно не завершит
  инициализацию, а production принимает только `https://iqro.forum`;
- `APP_DOWNLOAD_URL` задаёт встроенную запасную ссылку для функции «Поделиться».

Debug APK подписывается стандартным отладочным ключом. Release-сборка не использует
debug-подпись: CI или локальный защищённый контур должен передать `android/key.properties`
и keystore. Секреты не должны попадать в Git.

## iPhone и iPad

Требуются полный Xcode 26+, CocoaPods и Apple Developer signing только для установки
на физическое устройство или публикации. Проверить общую конфигурацию и собрать
неподписанный staging target можно так:

```bash
make mobile-ios-config-check
make mobile-ios-staging
```

iOS target имеет bundle ID `forum.iqro.app`, поддерживает iOS/iPadOS 14+, UIScene,
фоновое аудио, локальные уведомления и локализованные permission-тексты RU/EN/AR/TR.
Геопозиция запрашивается только во время использования приложения для расчёта времени
намаза; фоновый location-доступ не включён.

Аккаунт-зависимое обслуживание (sync, auth refresh и перепланирование уведомлений)
выполняется при запуске и каждом возврате приложения на передний план. Headless-задача
Workmanager пока намеренно не меняет аккаунтные данные: отдельный Dart isolate нельзя
безопасно согласовать с одновременным logout/handoff без межпроцессного durable fence.
Уже поставленные системные уведомления продолжают работать без открытого приложения;
на iOS горизонт плана ограничен 8 днями и продлевается при следующем открытии/возврате.

Фирменные app icon и launch mark для обеих платформ воспроизводимо экспортируются из
одной геометрии командой `cd clients/iqro_mobile && swift tool/generate_app_icons.swift`.

## Окружения без flavors

Отдельные flavors не нужны: один и тот же код компилируется с явной конфигурацией.

```bash
# Тестовый сервер
make mobile-android-staging

# Production AAB; без keystore получится только неподписанный compile-check
make mobile-android-production

# Production iOS compile-check; без signing и загрузки в App Store Connect
make mobile-ios-production
```

`APP_ENV=staging` принимает только `https://staging.iqro.forum`, а
`APP_ENV=production` — только `https://iqro.forum`. Это исключает случайный релиз,
направленный не в то окружение.

## Проверки

```bash
make mobile-check
make mobile-android-staging
```

Mobile CI закреплён на Flutter 3.41.4, проверяет lock-файлы, форматирование,
сгенерированные локализации, анализ, тесты, staging APK, production AAB и production
iPhone/iPad compile на Xcode 26.3. Gradle wrapper хранится в Git, а JAR и дистрибутив
проверяются официальными SHA-256.

## Архитектура

- `lib/app` — композиция зависимостей, маршрутизация и глобальные providers;
- `lib/core` — API, авторизация, SQLite, синхронизация, аудио и дизайн-система;
- `lib/features` — независимые вертикальные продуктовые модули;
- `lib/l10n` — RU/EN/AR/TR, включая полноценный RTL;
- `test` — unit-тесты модели сессии, настроек и API-моделей.

Детальные границы слоёв, offline-модель и порядок расширения описаны в
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Безопасность и приватность

- access/refresh token, installation ID и installation credential хранятся в
  Keystore/Keychain-backed secure storage;
- HTTP cleartext запрещён;
- API не следует HTTP redirect и принимает только соответствующий окружению HTTPS origin;
- резервное копирование данных приложения отключено;
- координаты используются только для запроса расчёта времени намаза и не добавляются
  в аналитику;
- технические UUID пользователя и устройства не показываются в пользовательском UI.

## Ограничения тестовой версии

Store-signing, Play Console, App Store Connect и push-доставка намеренно не включены.
Production endpoint поддержан через compile-time конфигурацию, но публикация требует
Android upload keystore либо Apple certificates/provisioning profiles. Книги и квизы
показаны как будущие разделы. Тексты переводов/тафсира не подменяются mock-данными:
интерфейс сообщает, когда утверждённый источник ещё не подключён.

Приоритет текущего мобильного этапа — Мусхаф и плеер. Мобильный Мусхаф пока публикует
только проверенный scan-вариант; web-варианты нельзя включать в native UI без отдельных page
assets, hit maps и offline manifest. Быстрый переход покрывает суру/аят, страницу, джуз, хизб
и руб аль-хизб. Текстовая читалка сохраняет размер арабского текста, межстрочный и межаятный
интервалы и режим без отвлечений; эти настройки не меняют геометрию scan-страниц. Полный
scan-Мусхаф адаптирован и для альбомной ориентации: страница сохраняет исходные пропорции,
симметрично скрывает только внешние боковые поля скана, заполняет ширину экрана и
просматривается по вертикали; горизонтальный жест по-прежнему перелистывает страницы.
При каждом повороте трансформация страницы сбрасывается к канонической компоновке новой
ориентации, поэтому альбомное смещение или масштаб не могут увести портретную страницу за
границы экрана. Портретная компоновка при этом остаётся неизменной. Полный
плеер уже переключает вид чтения и чтеца с сохранением текущей суры и безопасным переносом
позиции по совместимым таймкодам, а также качество аудиопотока без потери позиции. Мобильный
План использует общий с web server-authoritative goal, ручные и автоматические reading
sessions, историю, серии и prayer check-ins; при отсутствии сети последний dashboard остаётся
доступен только для просмотра. Автоматический зачёт учитывает активное время и только
последовательное продвижение, не превращая быстрый переход по Мусхафу в ложный прогресс;
неотправленная сессия повторно доставляется с тем же idempotency ID. Далее идёт
release/performance hardening. Первый проход уже изолирует часто обновляемый таймлайн от
статичной части развёрнутого плеера, объединяет одновременные запросы одной scan-страницы и
не пересчитывает её SHA-256 при каждом возврате, пока размер и системные timestamps файла не
изменились. Кэш проверок ограничен двенадцатью ближайшими файлами; первая проверка и любое
изменение файла по-прежнему проходят полную проверку WebP, размера и checksum.
Глобальная оболочка, Home, каталог чтецов и мини-плеер подписаны только на смысловое состояние
аудио и не перестраиваются на каждом обновлении позиции. Непрерывный position tick локализован
в transport-панели развёрнутого плеера и активной аудиокарточке Du’a.
Если один чтец опубликован отдельными backend-записями для разных видов чтения, приложение
сохраняет выбранный recitation/reciter ID, но разрешает портрет через объединённый профиль
человека. Поэтому каталог, Мусхаф, мини-плеер, полный плеер и новая системная media-карточка
используют один avatar URL.
Нижняя панель воспроизведения в полноэкранном scan-Мусхафе — тот же `IqroMiniPlayer`, что и
над основной навигацией: отдельной расходящейся реализации для читалки больше нет.
Прозрачность панели сохраняется обычной композицией цвета и рамки без постоянного
`BackdropFilter`: перелистывание scan-страниц не заставляет GPU заново размывать лежащий под
плеером фрагмент Мусхафа. При быстром перелистывании сохранения позиции выполняются строго
последовательно, а из промежуточной очереди остаётся только самая свежая страница; выбранный
аят по-прежнему записывается отдельно и немедленно.
На холодном старте обязательные dependency- и audio-platform инициализации выполняются
параллельно. Регистрация периодической Workmanager-задачи запускается только после первого
кадра и при ошибке регистрируется через FlutterError, но не удерживает пользователя на
splash-экране. На Redmi Note 7 debug APK после установки запускается примерно за 10 секунд,
а последующие старты нового процесса — за 5,1–5,4 секунды; это диагностическая точка для
debug-сборки, а не release-бюджет или доказательство ускорения первого post-install запуска.
Базовый profile-замер на том же Redmi Note 7 от 2026-09-04 показал 5,01 секунды для первого
запуска сразу после установки, затем 2,01 и 1,95 секунды для чистого старта процесса; возврат
из фона занимает 109–129 мс. Контрольные прогоны оптимизированного APK заняли 4,35–4,96
секунды сразу после переустановки и 1,90–1,94 секунды в устойчивых чистых стартах процесса.
Flutter startup trace
зафиксировал первый framework frame за 1,59 секунды,
из которых около 1,54 секунды пришлись на инициализацию engine и только 51 мс — на Flutter
framework после неё. PSS составил около 138 МБ на Home, 181 МБ после десяти перелистываний
Мусхафа и 168 МБ в развёрнутом плеере во время реального playback. Android MediaSession при
этом оставался active/playing с корректными сурой, чтецом, позицией и скоростью; в сценарии не
обнаружено Flutter fatal error, overflow или ANR. Воспроизводимый профильный APK собирается
командой `make mobile-android-profile-staging`.
Корневая навигация также создаёт вкладки лениво: на старте строится только Home, а Quran,
План, Audio и More впервые создаются при открытии. После первого посещения их состояние
сохраняется, поэтому оптимизация не сбрасывает экран и одновременно не запускает невидимые
provider/API-цепочки во время первого кадра.

Мобильные настройки намаза используют тот же revisioned профиль, что и web: поддержаны
стандартный и ханафитский расчёт Асра, ручные поправки шести времён и допустимые выбранным
методом правила высоких широт/полярного круга. Изменения сразу применяются локально,
перепланируют уведомления и при отсутствии сети ожидают безопасной синхронизации.
Если точная геолокация недоступна, пользователь может выбрать локально сохранённый город с
проверенной IANA timezone; от тех же координат приложение показывает направление Киблы как
географический азимут и явно не выдаёт его за показание живого магнитного компаса.
Месячный календарь рассчитывает каждый гражданский день тем же pinned local engine и теми же
пользовательскими настройками; после получения метода и location он доступен без сети.
Нативный средний виджет времени намаза реализован отдельно для Android (Jetpack Glance) и
iOS/iPadOS (WidgetKit), но получает один и тот же восьмидневный timeline из Flutter local
prayer engine. Он показывает ближайший намаз и все пять времён, самостоятельно переключается
по сохранённым абсолютным моментам, обновляется после смены location/метода/поправок/языка и
при запуске или возврате в приложение. Тап открывает экран намаза. Android может запросить
добавление виджета прямо из IQRO; на iOS система требует ручного добавления через галерею.
Для подписанной iOS-сборки App Group `group.forum.iqro.app` должен быть зарегистрирован в
Apple Developer и включён в provisioning profiles приложения и WidgetKit extension.

Подробный порядок подписанной публикации описан в
[`docs/RELEASE.md`](docs/RELEASE.md).
