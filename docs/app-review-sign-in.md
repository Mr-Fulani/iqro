# Вход для проверяющего App Store

Apple проверяет каждую версию приложения и просит данные для входа, если в приложении есть вход
(правило App Review 2.1(a)). У IQRO вход только по коду из письма, а проверяющий наших писем не
получает. Поэтому для одного адреса сервер принимает постоянный код и письмо с кодом на него не
отправляет. Так проверяющий сможет войти и проверить синхронизацию и удаление аккаунта
(правило 5.1.1(v)).

## Как устроено

- Адрес и код задаются в `services/backend/.env.production`: `QURAN_APP_REVIEW_EMAIL` и
  `QURAN_APP_REVIEW_PASSCODE`. Пока оба пустые, вход выключен — так по умолчанию.
- Письмо с кодом на этот адрес не уходит. Код проверяется как обычный: 10 минут и 5 попыток на один
  запрос кода. Адрес можно ввести с любыми заглавными буквами.
- Тот же код подтверждает удаление аккаунта и его отмену.
- Запросить код для этого адреса можно не больше 20 раз в сутки (по UTC) — на всех вместе,
  с любых устройств (`QURAN_APP_REVIEW_SIGN_IN_RATE`). С 5 попытками на запрос это не больше
  100 догадок в сутки из миллиона вариантов кода.
- Постоянный код никогда не открывает аккаунт сотрудника (`is_staff` или `is_superuser`): сервер
  отвечает отказом `account_link_unavailable`.
- Сервер не запустится, если задано только одно из двух, адрес неверный или код — не шесть цифр,
  одна цифра шесть раз или ряд подряд (`123456`, `987654`). Ошибка видна сразу при выкладке.
- Отчёты об ошибках (Sentry) не содержат переменных кода, поэтому постоянный код в них не попадает.
- Аккаунт создаётся сам при первом входе, как у любого нового пользователя. Если проверяющий
  удалит его, через 7 дней аккаунт сотрётся, а следующий вход создаст новый.

## Как включить

1. Завести новый адрес только для проверки Apple — в своём ящике или на своём домене, не рабочий и
   не адрес администратора. Адрес должен быть трудно угадать (не `review@…`, `apple@…`, `test@…`)
   и раньше не использоваться в IQRO: постоянный код откроет любой обычный аккаунт с этим адресом.
   Перед включением проверить в админке, что аккаунта с таким адресом нет.
   Доступ к ящику нужен: письмо с кодом туда не уходит, но ответы на обращения, отправленные из
   этого аккаунта, приходят на этот адрес.
2. Получить случайный код:

   ```bash
   python3 -c "import secrets; print(f'{secrets.randbelow(10**6):06d}')"
   ```

3. Дописать в `services/backend/.env.production` на сервере строки
   `QURAN_APP_REVIEW_EMAIL=<адрес>` и `QURAN_APP_REVIEW_PASSCODE=<код>` и сделать обычную
   выкладку (`make production-up`): бэкенд перечитает файл при пересоздании контейнеров.
4. Проверить: на сайте «Войти» → адрес → «Получить код» → код. Письма с кодом быть не должно.
5. Вписать адрес и код в App Store Connect: App Review Information → Notes и, для внешнего
   TestFlight, Beta App Review Information. Текст для Notes по-английски (подставить адрес и код):
   «Sign-in is optional. To test it, open More → Personal profile, enter <адрес>, tap Send code,
   enter the code <код> and tap Verify. No email is sent to this address.»

## Чего не делать

- Не входить в этот аккаунт с Android: проверяющий увидит Android в списке устройств
  (правило 2.3.10).
- Не хранить в этом аккаунте ничего личного.
- Не публиковать ни адрес, ни код. Кто знает адрес, может за сутки израсходовать 20 запросов кода,
  и до конца суток по UTC проверяющий получит «слишком много попыток». Если адрес или код стали
  известны посторонним — сменить оба на сервере и в App Store Connect.

Выключать вход после выхода версии не нужно: Apple проверяет и каждое обновление.

## Тесты

`services/backend/tests/test_app_review_sign_in.py`: выключено по умолчанию; вход постоянным
кодом без письма; другие адреса получают письмо; неверный код тратит попытки; код подтверждает
удаление; аккаунт сотрудника не открывается; общий суточный лимит при любом написании адреса и с
разных сетей; сервер не запускается с неверной настройкой.
