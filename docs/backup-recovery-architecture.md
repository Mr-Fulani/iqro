# Резервное копирование и восстановление production

## Статус на 13 сентября 2026 года

По сообщению владельца тестовый сервер временно удалён; боевой сервер ещё предстоит
создать. Старый адрес из release-отчётов не является текущей точкой доступа проекта.
Отчёты о staging backup/restore описывают исторические проверки, а не работающий сейчас
таймер. Сохранность объектов в прежнем R2 bucket отдельно не проверена.

Этот документ задаёт архитектуру восстановления нового production. Наличие скриптов
не означает, что резервирование уже включено. Локальная реализация дополнена и проверена;
до запуска требуется настройка доступов
и проверка восстановления на новой инфраструктуре. Команды и порядок внедрения:
[backup/recovery runbook](backup-recovery.md).

## Что сохраняем

| Объект | Целевая копия вне рабочего сервера | Реализация сейчас |
|---|---|---|
| Код и история Git | Версионный `git bundle --all` в независимом хранилище; проверка `git bundle verify` и восстановления в новый каталог | Есть `ops.recovery.snapshot`, проверка восстановления и opt-in daily systemd job |
| Релиз | Тег на проверенном commit `main`, commit SHA, версии образов/digests и ссылка на backup перед изменением данных | Добавлена команда `release` для локального тега и SHA/digest manifest; реальные теги ещё не созданы |
| PostgreSQL | Custom-format dump, SHA-256 и recovery manifest в приватном S3-совместимом bucket | Есть backup, verify, offsite upload/download и isolated restore-check |
| Медиа | Отдельная копия объектов и manifest с ключами, размерами и SHA-256; сохранение предыдущих версий | Есть потоковый snapshot объектов, SHA-256, восстановление в отдельный bucket |
| Секреты и конфигурация | Зашифрованная копия env и конфигурации инфраструктуры вне сервера; ключ восстановления хранится отдельно | Есть шифрование через age по явному списку файлов и восстановление в новый приватный каталог |

Публичный GitHub не должен получать `.env`, ключи, дампы или приватные recovery manifests.
Bundle содержит Git-объекты и refs; он не включает незакоммиченные/игнорируемые файлы,
содержимое Git LFS и отдельные репозитории submodules. Если они появятся, их нужно включить
в инвентарь резервирования отдельно. Рабочая копия разработчика не заменяет backup job.

PostgreSQL dump не содержит медиа. Рабочий media bucket не заменяет независимую копию.
Исходные каталоги и скрипты импорта не гарантируют восстановление недоступного внешнего
источника: необходимые для релиза объекты должны быть доступны из резервной копии.

## Размещение и доступ

- Production использует собственные секреты, БД и префикс `production`; staging-данные
  не становятся production-данными автоматически.
- Backup bucket приватный, отделён от публичного media bucket и имеет отдельный token.
  Для нового сервера нужно проверить ограничения token по IP: старый staging IP не подходит.
- Recovery-доступ должен сохраняться при потере application host. Ключ расшифровки
  конфигурации нельзя хранить только на этом host или внутри зашифрованного архива.
- Для защиты от компрометации сервера целевой backup writer не должен иметь возможности
  удалить все исторические копии. Выбор отдельного аккаунта/хранилища или механизма
  неизменяемости и проверка его прав остаются задачей настройки провайдера.
- История, checksum и успешная загрузка не заменяют пробное восстановление.

## Периодичность и контроль

Начальная проектная цель для БД — потеря не более 24 часов изменений при исправном
ежедневном offsite backup. Это целевой RPO, а не подтверждённая гарантия. При росте
пользовательских данных нужно пересмотреть частоту и необходимость PostgreSQL PITR/WAL.
RTO пока не измерен; его фиксируют по времени восстановления на новом сервере.

Код сохраняется после каждого релиза и ежедневно при изменениях refs. Медиа копируются
до публикации новой версии, изменяемые объекты — ежедневно. Зашифрованная конфигурация
обновляется после изменения секретов, DNS/storage-настроек или инфраструктуры.

`quran-backup@.timer` назначает ежедневный запуск в 01:15 UTC с задержкой до 15 минут,
`quran-recovery@.timer` — в 02:00 UTC с такой же задержкой. Существующий heartbeat расширен:
проверяет локальный дамп и receipts последней успешной offsite-загрузки обоих job с учётом
возраста исходных данных. Ошибки направляются в тот же внешний монитор, без второго
канала уведомлений. При полной потере сервера монитор замечает отсутствие heartbeat.

Полное скачивание и пробное восстановление выполняются при вводе production,
после изменения процесса резервирования и затем ежемесячно. Записываются дата, SHA-256,
commit/schema версии, длительность и результаты проверки приложения. Небольшие изменения
текста и стилей не требуют нового полного дампа или внепланового recovery drill.

## Сохранение старых копий

Очистка выполняется только после отдельного согласования владельцем точных целей и
последствий. Наличие retention-параметров или создание нового сервера такого разрешения
не даёт.

Реализовано согласованное правило: три последние успешные локальные копии каждого
типа, во внешнем хранилище — объединение семи ежедневных и четырёх еженедельных.
Общие объекты сохраняются, пока на них ссылается хотя бы один сохраняемый snapshot.
Расчёт создаёт точный список удаления с размерами и hash; применение возможно только
после одобрения списка и повторной проверки неизменности инвентаря. Обычное создание
копии не запускает удаление. Инструкция: [план и применение](backup-recovery.md#предварительный-расчёт).
Неуспешные попытки, неизвестные файлы и lifecycle провайдера требуют отдельного разбора;
до применения одобренного плана копии продолжают занимать место.

## Восстановление после потери сервера

1. Получить выбранный release manifest, Git bundle, дамп БД, manifest медиа и
   зашифрованную конфигурацию через независимый recovery-доступ.
2. Проверить контрольные суммы, восстановить Git в новый каталог и выбрать commit
   совместимый со схемой выбранного дампа. Не применять автоматически текущий `main`
   к старому дампу без проверки совместимости.
3. Подготовить изолированную инфраструктуру и восстановить БД в новую базу. Рабочую БД
   не перезаписывать. Существующий `restore.sh` разрушителен для выбранной базы и требует
   отдельного явного разрешения; `restore-check.sh` предназначен для изолированной пробы.
4. Восстановить медиа и конфигурацию, проверить соответствие ключей объектов ссылкам
   в БД. В пробной среде отключить отправку писем и фоновые задания с внешними эффектами.
5. Проверить запуск приложения, каталог, чтение, закладки/прогресс и доступ к медиа.
   Зафиксировать фактические RPO/RTO и недостающие данные.
6. Переключить трафик после успешной проверки. Сохранить старые копии и возможность
   отката. Включить backup/monitoring и подтвердить получение уведомления об ошибке.

## Что завершить до ввода боевого сервера

Код пунктов 1–5 первоначального плана подготовлен и проверяется локальными тестами:
сохранение копий, Git/releases, media/config, расширение существующего мониторинга и
изолированное восстановление. Production пока не активирован.

На новом сервере остаётся:

1. Настроить независимое хранилище, ограниченные credentials и recovery-доступ.
2. Передать публичный age recipient, явно перечислить файлы конфигурации и задать
   объём/число media объектов; приватный recovery key оставить вне сервера.
3. Подготовить отдельный полный Git mirror, production env и существующий внешний монитор.
4. Создать первые копии, выполнить полный recovery drill и smoke-проверку приложения,
   измерить RPO/RTO и подтвердить доставку уведомлений.
5. После успешной проверки включить таймеры. Реальные release tags создаются для
   проверенных релизов, а не задним числом для текущей разработки.
