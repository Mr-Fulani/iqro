## Область и итог

Проверены существующий MVP-аудит, audio roadmap/ADR, серверные модели,
каталог, публикация и playback endpoints, выбор аудио в web и Flutter.

production-базы, всего приложения или поведения Android/iOS на устройствах.

Требование пользователя: новые чтецы и добавленные к ним записи должны быть
доступны в плеере, но не в Мусхафе и учебном чтении. Под учебным чтением в этом
отчёте учтены Reader, действия над аятом и Memorization/заучивание.

**Нужны улучшения.** Текущая реализация разделяет настройки и исключает записи
без таймкодов из контекстного чтения. Но она не выражает отдельный редакционный
запрет «только плеер»: наличие полных таймкодов автоматически включает две роли.

Код приложения, данные, CI и deployment в рамках аудита не изменялись.
Существующее изменение `services/web/next-env.d.ts` сохранено.

## Замечания и приоритеты

### 1. Высокий: отсутствует политика «только плеер»

Доказательства:

- [Модель версии](../services/backend/src/quran_backend/modules/audio/models.py):
  есть права streaming/offline, но нет разрешений на контекстное чтение.
- [Serializer](../services/backend/src/quran_backend/modules/audio/serializers.py),
  `get_capabilities`, строки 220–227: `ayah_playback` и `memorization` равны
  `timings_complete`.
- [Variant resolver](../services/backend/src/quran_backend/modules/audio/variant_resolver.py):
  native adapter строит эти возможности по тому же признаку.

Следствие: импорт нового полного timed-релиза делает его доступным в Мусхафе и
заучивании. Текущее скрытие untimed-записей не гарантирует требование пользователя.

Предложение: хранить разрешённые сценарии у конкретной версии записи. Для новых
версий по умолчанию разрешать только Listening; Mushaf/Reader и Memorization
включать отдельно и явно. Возможность равна пересечению редакционного разрешения,
прав streaming, опубликованности и технической пригодности.

Не ставить единый запрет на человека: у одного чтеца могут остаться прежние
одобренные учебные записи и появиться новые записи только для плеера.
При миграции сохранить действующие разрешения старых версий, затем применить
новое правило к новым версиям. Не удалять и не искажать таймкоды для скрытия UI.

### 2. Высокий: серверные пути должны применять одну политику

В [memorization service](../services/backend/src/quran_backend/modules/memorization/services.py),
`_published_recitation`, строки 375–416, проверяется доступность и покрытие диапазона.
В legacy ayah endpoint в [audio API](../services/backend/src/quran_backend/modules/audio/api.py),
строки 433–440, проверяется наличие публичной записи и сегмента.
Отдельное разрешение «только плеер» проверить сейчас невозможно.

При введении политики применить её к serializer, resolver, legacy ayah endpoint,
созданию/изменению плана и запуску существующего учебного плана. Прямой запрос
с ID записи не должен обходить запрет через скрытый UI.

Покрытие диапазона и разрешение роли — отдельные проверки. Сейчас план может
принимать конкретный покрытый диапазон, даже если каталог не рекламирует полное
покрытие Quran; это следует явно отразить в контракте, не смешивая с запретом роли.

Учесть старые приложения, игнорирующие capabilities, и сохранённые каталоги:
серверный отказ нужен даже после обновления UI; rollout должен проверять
совместимость старых клиентов и обновление кеша.

### 3. Средний: пагинация ограничивает рост каталога

- [Web Audio](../services/web/app/audio/page.tsx), строки 66–68 и 101–104:
  используются результаты одной страницы чтецов и записей.
- [Web Mushaf](../services/web/components/MushafAudioPlayer.tsx), строки 109–112:
  фильтрация только первой страницы записей.
- [Flutter AudioRepository](../clients/iqro_mobile/lib/features/audio/audio_repository.dart),
  `reciters`/`recitations`: один запрос с `page_size: 100`, без обхода `next`.
- Backend page size по умолчанию — 50, максимум для этих каталогов — 100.

При превышении этих границ часть новых чтецов/записей исчезнет из выбора.
Использовать общий cursor loader или явную постраничную загрузку с поиском.
В web уже есть `getAllRecitations`, но он не используется во всех этих местах
и ограничен 20 страницами без сообщения о неполном результате.

### 4. Средний, зависит от формата контента: отдельные записи скрыты

[public_recitation_base](../services/backend/src/quran_backend/modules/audio/selectors.py),
строки 37–54, требует 114 сур с default renditions для публичного каталога и
традиционных playback endpoints. Это сознательная защита от неполного импорта,
описанная в audio API, а не случайная ошибка.

Если под «записи к чтецу» подразумеваются отдельные суры или разные исполнения,
нынешний публичный контракт недостаточен. Рекомендация — отдельный явно
опубликованный тип listening collection с доступными треками и показом покрытия.
Полный Quran-релиз и пилотный импорт сохраняют прежние правила. Не ослаблять общий
selector без пересмотра потребителей, sitemap и release contract.

### 5. Средний: исполнение может исчезнуть при дедупликации

[Web catalog](../services/web/lib/reciter-catalog.ts), `latestRecitationsByVariant`,
группирует по человеку, стилю и Quran edition, оставляя последнюю публикацию.
Разные записи одного стиля будут сведены к одной.

`recitationsForReciters` в [Flutter repository](../clients/iqro_mobile/lib/features/audio/audio_repository.dart)
группирует только по стилю и ранжирует по таймкодам/покрытию. Текущих вызовов этого
метода в `lib` при поиске не найдено: это риск будущего повторного использования,
а не подтверждённая ошибка активного экрана.

Отделить идентификатор исполнения/коллекции от версии публикации. Выбирать
последнюю версию внутри одного исполнения, сохраняя разные исполнения в плеере.

### 6. Средний: legacy fallback Flutter мягче, чем web

[Flutter models](../clients/iqro_mobile/lib/features/audio/audio_models.dart),
строка 217 и fallback в `supports`: отсутствие capabilities компенсируется
`timings.available`. Web требует также `timings.complete === true`.

Старый кеш с частичными таймкодами может предложить запись в учебном сценарии.
Согласовать fallback, проверять completeness и обеспечить обновление кеша после
введения новой политики. Само completeness не заменяет редакционное разрешение.

## Добавление чтецов и записей: рекомендуемый процесс

1. Создать или выбрать канонический профиль чтеца; прикрепить новую версию записи.
2. По умолчанию оставить только Listening, независимо от наличия таймкодов.
3. Проверить файлы/URL, длительность, источник, права и доступные суры.
4. Перед публикацией показать оператору итог: «Плеер — да; Мусхаф/Reader — нет;
   Заучивание — нет» и список доступных треков.
5. Публиковать версию целиком после проверки; обновлять каталог/кеш и сохранять
   предыдущую версию для отката.

Существующая admin-модель и upload-команда дают базу для managed assets; массовое
добавление файлов стоит оформить как импорт manifest с предварительным отчётом,
проверкой дубликатов и возобновлением. Это предложение, не реализованный механизм.

## Критерии приёмки улучшений

- Новая запись с полными таймкодами видна в плеере и отсутствует в Mushaf, Reader,
  меню аята и Memorization.
- Прямой запрос ayah playback и сохранение учебного плана с её ID отклоняются.
- Новая запись существующего чтеца не изменяет доступность его старых разрешённых
  учебных записей и не перезаписывает соседние preferences.
- Разные исполнения одного стиля сохраняются в каталоге плеера.
- Каталоги с количеством выше одной страницы отображаются полностью.
- Старый кеш, отозванная версия и старые клиенты проверены отдельно.
- При поддержке неполных listening collections UI предлагает только имеющиеся суры.
