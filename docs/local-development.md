# Локальный запуск команды

Общего тестового сервера нет. Backend работает на компьютере каждого разработчика;
браузер и мобильное приложение получают содержимое из его API.

## Инструменты

Для основного пути нужны Git, Python 3.9+, Docker Desktop с Compose v2 и `make`.
На macOS `git`/`make` устанавливаются с `xcode-select --install`; Docker Desktop
должен быть запущен. На Linux можно использовать Docker Engine с Compose plugin.
`make dev-doctor` проверяет подключение, миграции и готовность данных.

Host Python 3 используется только управляющим скриптом. Backend Python 3.14 и Node.js
устанавливаются Docker-образами. `uv` — менеджер Python-зависимостей; основной Docker-путь
обходится без его установки. Для работы с backend вне Docker установите `uv`, затем
в `services/backend` выполните `uv sync --frozen --all-groups`.
Для запуска backend вне Docker также нужны доступные PostgreSQL/Redis и переменные
окружения процесса: Django самостоятельно `.env` не загружает.

Mobile: Flutter 3.41.4, Android SDK либо Xcode и CocoaPods. Выполните `flutter doctor`.
Для web вне Docker нужна версия Node.js из `services/web/package.json`, затем `npm ci`.

## Первый запуск

```bash
make dev-init
# В services/backend/.env указать QF_CLIENT_ID, QF_CLIENT_SECRET, QF_ENV
make dev-up
make dev-data
make dev-doctor
make mobile-run
```

`QF_ENV=prelive` или `production` должен соответствовать выданным ключам **провайдера**.
Он не выбирает сервер приложения: приложение продолжает работать с локальным backend.
Секреты нужны только backend. После изменения `.env` повторите `make dev-up`, чтобы
контейнер получил новые значения. Существующий `.env` команда `dev-init` сохраняет.

`dev-up` собирает образы, запускает PostgreSQL/Redis, применяет миграции и запускает
API, web и фоновые задачи. При наличии старой БД и неприменённых миграций создаёт
дамп в `.dev/backups/` и проверяет его через `pg_restore --list`; при ошибке останавливается.
Проверка структуры архива не заменяет полноценную пробу восстановления production-бэкапа.

Сайт: http://localhost:3000, API: http://localhost:8000/api/v1,
документация API: http://localhost:8000/api/docs.

## Откуда берётся содержимое

| Данные | Подготовка | Хранение |
| --- | --- | --- |
| Канонический Коран | Закреплённый корпус Tanzil через публичное зеркало; SHA-256 проверяется | Локальная PostgreSQL |
| Слова и структура страниц | Content Sync Quran.Foundation | Локальная PostgreSQL |
| Соответствие аятов страницам | Проверенные 604 страницы QF KFGQPC, source 5 | `AyahPageMapping` |
| Web-Мусхаф | Слова из локального API, официальные шрифты QF | Браузер |
| Mobile-Мусхаф | Генерация KFGQPC из слов и официального шрифта в отдельном Docker-образе | `media/` + PostgreSQL |
| Ду’а | Полные встроенные каталоги из миграций; `dev-data` повторно проверяет/публикует их | Локальная PostgreSQL |
| Переводы и тафсиры | `make dev-data DEV_DATA_ARGS=--extras` | Локальная PostgreSQL |
| Аудио | Отдельный импорт выбранного чтеца, пример ниже | Метаданные в БД; поток с источника |
| Намаз | Методы из миграций и расчёт для выбранного места/даты | Локальный backend |

Миграции уже включают полный «Хисн аль-Муслим» и коранические ду’а из репозитория.
`dev-data` повторно проверяет их импорт и публикацию без дублирования записей,
выполняет QF sync выбранного KFGQPC (source 5), импорт канонического текста, создание всех
604 мобильных страниц и локальную публикацию. Это не вызов внешнего API из телефона.
Первая подготовка требует сети, времени на рендеринг и места для образов/страниц.
Рендер выполняет две независимые страницы одновременно и сравнивает пиксели PNG/WebP
для каждого размера. Публикация происходит только после проверки всех 604 страниц.
Промежуточные файлы в `.dev/` проверяются и используются повторно; при изменении источника
или рендерера создаётся отдельный набор. Старые файлы автоматически не удаляются.
На компьютере с 8 ГБ RAM дождитесь окончания `dev-data`, прежде чем одновременно
запускать Android-сборку и эмулятор. Локальный Celery ограничен двумя процессами.

Для работы только над сайтом: `make dev-data DEV_DATA_ARGS=--web-only`. Канонический
текст и страницы QF будут доступны, но мобильная читалка потребует полного `dev-data`.

Web использует доступные макеты QF 1, 5, 19; выбирается KFGQPC 5, если он доступен.
Дополнительные web-макеты можно загрузить командой `sync_quran_foundation_mushafs --source-id 1 --source-id 19`
через `docker compose --env-file services/backend/.env exec backend python manage.py`.
Каждый набор выбранных источников имеет отдельный checkpoint. Неполный посторонний
макет провайдера не блокирует основной локальный импорт source 5.
Локально для mobile автоматически готовится KFGQPC 5. Остальные макеты остаются
поддерживаемыми и появляются в мобильном выборе после отдельной полной публикации.
Вход на экран при пустом каталоге показывает отсутствие данных без фиктивной страницы.
Периодические полные импорты Quran.Foundation отключены в local-настройках:
содержимое обновляется явно через `dev-data` или нужную команду импорта.
Фоновые задачи напоминаний и обслуживания локальной БД продолжают работать.

Пример потокового аудио одного чтеца со всеми сурами:

```bash
docker compose --env-file services/backend/.env exec backend python manage.py \
  sync_quran_foundation_audio --reciter-id 159 --all-surahs \
  --content-version local-dev-v1 --publish --resume
```

Это не скачивает все аудиофайлы в Git/media. Чтобы получить обновлённую неизменяемую
версию содержимого позже, задайте новое значение `--content-version`. Полный каталог
всех чтецов необязателен для обычной разработки и импортируется отдельно.

## Подключение телефона

| Устройство | API_BASE_URL |
| --- | --- |
| Android Emulator | `http://10.0.2.2:8000` (автоматически) |
| iOS Simulator | `http://127.0.0.1:8000` (автоматически) |
| Физический телефон в Wi-Fi | `http://<LAN-IP-компьютера>:8000` |
| Android по USB с `adb reverse tcp:8000 tcp:8000` | `http://127.0.0.1:8000` |

```bash
make mobile-run MOBILE_ARGS="--dart-define=API_BASE_URL=http://192.168.1.20:8000"
```

Для Wi-Fi замените пример реальным IP и добавьте его в `DJANGO_ALLOWED_HOSTS` в `.env`,
затем `make dev-up`. Разрешите подключение в локальном firewall; на iOS подтвердите
доступ к локальной сети. URL указывается **без** `/api/v1`: приложение добавляет путь.
HTTP и локальные медиа разрешены только в debug/local. Profile/release локальный режим
отклоняют; их требования HTTPS не ослаблены.

После полного `dev-data` можно проверить контракт настоящего API мобильным клиентом:

```bash
cd clients/iqro_mobile
IQRO_LOCAL_API_URL=http://127.0.0.1:8000 \
  flutter test test/integration/local_backend_mushaf_test.dart
```

Тест проверяет каталог, offline-manifest всех 604 страниц и 6236 аятов, контрольные
суммы и декодирование первой/последней страницы. Без переменной окружения этот тест
пропускается; обычные тесты не зависят от запущенного API и ключей источника.

## Проверка проблем

- `make dev-doctor`: различает неприменённые миграции, отсутствующий корпус, QF и медиа.
- `QF_CLIENT_ID/QF_CLIENT_SECRET` отсутствуют: заполните backend `.env` и повторите `dev-up`.
- Ошибка авторизации QF: проверьте окружение ключей и выданный доступ к Content Sync.
- Web работает, mobile пуст: после `--web-only` нужен полный `make dev-data`.
- Телефон не соединяется: проверьте LAN IP, `DJANGO_ALLOWED_HOSTS`, firewall и порт 8000.
- Ошибка несовместимого существующего корпуса: импорт сохранил старую БД. Не удаляйте
  её и не обходите проверку — подготовьте отдельную миграцию соответствия данных.
- Старый адрес страниц отвечает 410: обновите клиент; страницы теперь в `mushaf-renditions`.

Ни дамп коллеги, ни его папка `media/`, ни PDF не нужны для нового окружения.
Исторические поля и UUID старой БД сохраняются для прогресса, закладок и безопасного перехода.
