# Внедрение резервного копирования и восстановление

Код подготовлен без обращения к прежнему staging-серверу. Новый production вводится
после проверки доступа к хранилищу, полного восстановления и доставки уведомлений.
Состав и ограничения: [архитектура](backup-recovery-architecture.md).

## Уже используемые механизмы

- PostgreSQL: прежние `backup.sh`, `verify.sh`, `restore-check.sh` и `offsite.py`.
- Все загрузки и скачивания: общий S3-клиент, SHA-256, проверка размера/metadata и
  публикация скачанного файла только после проверки в `ops/postgres/offsite.py`.
- Уведомления: существующий `ops/monitoring/heartbeat.py` и внешний Healthchecks.
  Второго провайдера уведомлений или отдельного канала ошибок нет.
- Зависимости S3: существующий `boto3` из backend lock-файла.
- Git: стандартный [bundle](https://git-scm.com/docs/git-bundle).
  Конфигурация шифруется стандартным [age](https://github.com/FiloSottile/age), без
  собственной криптографии и без промежуточного plaintext-архива на диске.

## Локальная проверка

Нужны Git, `age`/`age-keygen` и уже подготовленный backend Python runtime. Тесты
используют временные репозитории, тестовые ключи и хранилище в памяти. Реальные
GitHub/S3/Healthchecks, ключи пользователя и серверы не используются.

```bash
make recovery-test
```

Проверяются полный цикл создания/скачивания snapshot, восстановление Git refs и
медиа, шифрование/расшифровка, повреждённые данные, смена объектов во время backup,
недоступность хранилища, сохранение старых дампов и запрет перезаписи существующих
файлов. Новые тесты добавлены в существующий Backend CI; отдельного CI pipeline нет.

## Подготовка нового production

1. Подготовить backend runtime из существующего lock-файла:
   `uv sync --frozen --no-dev --project services/backend`. Systemd использует
   `/opt/quran/services/backend/.venv/bin/python`. Установить Git и `age` из
   доверенного пакета ОС. Контейнеры приложения ради этих инструментов не меняются.
2. На доверенном recovery-компьютере создать `age` identity и проверить её сохранение
   в независимом secret store. На сервер передать только публичного получателя `age1…`.
   Приватный ключ не включать в конфигурацию backup job и в шифруемый им архив.
3. Создать `/etc/iqro/production-recovery.json` на основе
   `ops/recovery/config.example.json`, права `0600`. Указать точные пути конфигурации,
   публичных получателей и бюджет media. По умолчанию пример допускает до 50 GiB и
   100 000 объектов; подобрать лимиты под доступный диск и измеренный объём.
4. Подготовить отдельный полный bare-репозиторий:
   `git clone --mirror https://github.com/Mr-Fulani/iqro.git /opt/iqro-source.git`.
   Этот путь не должен быть рабочей копией разработчика. Планировщик обновляет
   ветки/tags без `prune`; удалённые на GitHub ветки сохраняются в локальном инвентаре.
   При конфликте существующего тега refresh завершается ошибкой, тег не перезаписывается.
5. Создать `/etc/iqro/production-recovery.env` по
   `ops/recovery/recovery.env.example`, права `0600`. Использовать те же
   `BACKUP_OBJECT_STORAGE_*`, что у PostgreSQL, и отдельный read-only token рабочего
   media bucket. Секреты не передавать аргументами CLI и не помещать в Git. Проверить
   новые IP-ограничения storage token; адрес удалённого staging не подходит.
6. В production env задать абсолютные `QURAN_BACKUP_DIR=/opt/quran/backups` и
   `QURAN_BACKUP_STATUS_DIR=/opt/quran/backups/status`. В recovery env путь
   `RECOVERY_STATUS_FILE=/opt/quran/backups/status/recovery.json` должен совпадать
   с каталогом, который читает heartbeat. Убедиться в достаточном свободном месте.
7. Настроить существующий монитор скрытым вводом его success/failure URL:

```bash
python3 -m ops.monitoring.configure \
  --output /etc/iqro/production-heartbeat.env \
  --site-url https://iqro.forum \
  --backup-dir /opt/quran/backups \
  --backup-status-dir /opt/quran/backups/status \
  --environment production
```

Failure URL нужен для немедленной отправки ошибки job; при его отсутствии внешний
монитор заметит прекращение успешных heartbeat после своего grace period.

Systemd installer только устанавливает unit-файлы, не включает их. После настройки
выполнить вручную оба backup job, затем проверку восстановления. Только после успеха
включить `quran-backup@production.timer`, `quran-recovery@production.timer` и
`quran-heartbeat@production.timer`. Это действия на будущем сервере, сейчас они не выполнены.

## Создание и поиск копий

Команды ниже предполагают уже настроенное окружение с `BACKUP_OBJECT_STORAGE_*`,
`MEDIA_OBJECT_STORAGE_*` и `RECOVERY_STATUS_FILE`; systemd получает его через
`EnvironmentFile`. Не копировать секреты в историю команд.

```bash
make production-backup-offsite
make recovery-backup RECOVERY_ARGS='--config /etc/iqro/production-recovery.json'
make recovery-list
```

Планировщик recovery выполняет `ops.recovery.scheduled`: сначала refresh отдельного
Git mirror, затем тот же `ops.recovery.snapshot backup`. Ручная команда backup
сохраняет refs как есть и не делает сетевой fetch.

Набор содержит Git bundle со всеми refs, `configuration.tar.age`, media manifest и
медиа. Если задан `release_manifest`, включает `release.json` с проверкой тега и SHA.
Объекты S3 хранятся по SHA-256, поэтому одинаковые файлы между наборами повторно не
загружаются. Медиа читаются потоком; до и после копирования сравниваются инвентарь и
ETag. Публикацию медиа на время копирования нужно остановить либо использовать
неизменяемые версии объектов: это не транзакционный снимок изменяемого bucket.

Итоговый manifest загружается последним, под уникальным ключом
`<prefix>/<environment>/recovery/snapshots/<timestamp>-<id>.json`. Незавершённая
попытка не публикует успешный manifest/receipt. Команда `list` позволяет найти копии
после полной потери сервера; локальный receipt не является единственным способом доступа.
Копию receipt с SHA-256 желательно хранить отдельно, вместе с материалами релиза.

## Восстановление без изменения работающей среды

Выбрать конкретный snapshot key из `make recovery-list`, затем скачать в **новый** каталог:

```bash
make recovery-restore RECOVERY_ARGS='--snapshot-key <key-from-list> --output /srv/recovery/drill-2026-09-13'
services/backend/.venv/bin/python -m ops.recovery.snapshot decrypt-config \
  --snapshot /srv/recovery/drill-2026-09-13 \
  --identity /secure/recovery-identity.txt \
  --output /srv/recovery/drill-2026-09-13-config
```

После `restore` появляются `repository.git`, файлы медиа с безопасными hash-именами,
`media.json` с оригинальными S3 keys и `verified.json`. Расшифровка конфигурации
полностью проверяет `age` authentication до записи plaintext и создаёт только новый
каталог с правами `0700` и файлы `0600`. Ни `.env` приложения, ни текущая БД не заменяются.

Для проверки восстановления медиа создать **другой** пустой recovery bucket и
настроить `MEDIA_OBJECT_STORAGE_*` на него с правами записи. Затем:

```bash
services/backend/.venv/bin/python -m ops.recovery.snapshot restore-media \
  --snapshot /srv/recovery/drill-2026-09-13
```

Команда восстанавливает оригинальные ключи и Content-Type, проверяет локальные суммы
и удалённые metadata. Она откажется писать в исходный media bucket или backup bucket,
а существующий ключ с другим содержимым не перезапишет. Переключение приложения/CDN
на восстановленный bucket выполняется отдельно после smoke-проверки.

Для БД использовать существующий isolated drill:

```bash
make production-backup-offsite-restore-check
```

Каждый запуск скачивает дамп в новое имя; прошлые скачанные дампы сохраняются.
Проверка восстановления БД остаётся в прежнем `restore-check.sh`. После полного
восстановления на новом сервере отдельно проверить приложение: каталог, чтение,
закладки/прогресс и media URLs, измерить длительность и фактическую потерю данных.
При несовпадающих временах БД/media snapshot проверить ссылки БД на объекты;
скрипты не обеспечивают атомарный общий снимок БД и object storage.

## Релизы

После успешного PR в `main`, CI и получения digests образов подготовить тег и manifest:

```bash
make recovery-release RECOVERY_ARGS='--repository /path/to/clean/repo --tag v1.0.0 --image web=registry/iqro-web@sha256:<64-hex-digest> --output /secure/releases/v1.0.0.json'
```

Указать каждый образ релиза отдельным `--image`. Команда требует чистую рабочую копию
и HEAD на commit `main`, создаёт локальный annotated tag и записывает SHA/digests.
Тег другого commit не передвигается. Публикация тега и деплой не запускаются.
В recovery config указать путь `release_manifest` на этот файл и добавить его к
инвентарю нового релиза. После явной публикации тега scheduled mirror получит его
при следующем fetch. До первого релиза поле может быть `null`.

## Контроль ошибок и сохранение копий

PostgreSQL и recovery job записывают небольшие receipts в общий status directory.
Время источника сохраняется отдельно от времени загрузки: повторная отправка старого
дампа не скрывает просрочку. Heartbeat проверяет обе успешные receipts и свежесть
источников, затем отправляет прежний success ping. Неполные/повреждённые receipts,
ошибка job или слишком старые данные блокируют success ping. `ExecStopPost` сообщает
ошибку через тот же failure URL и помечает соответствующую receipt как failed.
Успех одного job не сбрасывает ошибку другого.

Receipt подтверждает последнюю проверенную загрузку, а не постоянную доступность всех
объектов. Полное скачивание и recovery drill нужны ежемесячно и после изменения процесса.
Доставку failure/recovery уведомления проверяют на новом сервере отдельно.

Каталог дампов дополнительно защищён `.backup.lock` от одновременного ручного и
планового запуска. При принудительном завершении процесса/перезагрузке может остаться
lock: прежде чем снимать его вручную, убедиться, что backup больше не выполняется.
Скрипт не снимает неизвестный lock автоматически.

## Хранение: 3 локальных, 7 ежедневных и 4 еженедельных

Согласованное правило реализовано в одном модуле `ops/recovery/retention.py`:

- Локально сохраняются три последние успешные копии каждой БД и три последних
  полных набора Git/media/config. Неуспешная попытка не занимает место успешной копии.
- Во внешнем хранилище сохраняется объединение последней копии за каждую из семи
  последних представленных UTC-дат и последней копии за каждую из четырёх последних
  представленных ISO-недель. Дневная и недельная копия могут совпадать, поэтому
  обычно сохраняется меньше 11 копий каждого типа. При редких запусках сохраняются
  представленные даты/недели, а не только последние 7/28 календарных суток.
- Цель PostgreSQL `latest.json` сохраняется дополнительно, даже если она старше
  обычного окна. Сам указатель не удаляется.
- Общие объекты Git/media/config удаляются только когда на них больше не ссылается
  ни один сохраняемый remote snapshot. Сначала удаляются устаревшие manifests,
  затем ставшие ненужными объекты. Простая очистка S3 по возрасту запрещена.

Создание копий само по себе не удаляет данные. Согласно рабочему соглашению владельца,
**перед фактическим удалением нужно одобрение точных целей и их объёмов**. Согласование
правила хранения не заменяет одобрение конкретного списка. Неполные наборы, старые дампы
без доказательства успешной загрузки, неизвестные файлы и объекты незавершённых загрузок
не очищаются автоматически и отмечаются/сохраняются для отдельного разбора.

### Предварительный расчёт

После успешного выполнения обоих backup job создать новый план (секреты уже переданы
в окружение тем же способом, что для recovery-команд выше):

```bash
make recovery-retention-plan RECOVERY_ARGS='--recovery-dir /opt/quran/backups/recovery --status-dir /opt/quran/backups/status --output /secure/retention-review-2026-09-13.json'
```

Команда только читает копии и создаёт JSON со списками `keep_local`, `keep_remote`,
`delete`, точными путями/S3 keys, bucket/endpoint, размерами и суммой `delete_bytes`.
Она выводит SHA-256 канонического содержимого плана для его одобрения. План нужно
показать владельцу целиком в части целей удаления и объяснить освобождаемый объём.
Существующий plan-файл не перезаписывается. Не генерировать запас планов по расписанию:
план нужен непосредственно перед согласованной очисткой.

Планировщик откажется работать, если последнее копирование БД или recovery завершилось
ошибкой, receipts просрочены/отсутствуют, копия повреждена, manifest неизвестного формата
или потерян один из общих объектов. Механизм переиспользует существующую проверку
backup receipts, S3-клиент и общий валидатор snapshot из восстановления.

### Применение одобренного списка

Только после явного одобрения владельцем целей и последствий:

```bash
make recovery-retention-apply RECOVERY_ARGS='--plan /secure/retention-review-2026-09-13.json --approved-plan-sha256 <approved-sha256>'
```

Hash связывает команду с просмотренным списком; наличие флага само по себе не является
разрешением пользователя. Перед любым удалением заново проверяются успешность jobs,
весь инвентарь, контрольные суммы, sizes/ETag, локальные inode/mtime, storage scope
и ссылки manifests. Любое изменение требует нового плана и его одобрения. При ошибке
S3 или файловой операции выполнение останавливается; после частичного выполнения
нужно заново рассчитать и согласовать оставшиеся цели, не обходить проверку hash.

Загрузки и применение плана используют общий `.storage.lock` в status directory.
Для production это **один backup host**: все writers должны использовать эти CLI и
один физический status directory. В Compose `/backup-status` должен указывать на тот
же host-каталог, что `RECOVERY_STATUS_FILE` и `--status-dir`. Это локальная блокировка,
она не координирует сторонние S3 writers или другой сервер; при переносе на несколько
backup hosts потребуется распределённая блокировка/дополнительная защита провайдера.

После успешной отправки PostgreSQL сохраняется неизменяемая receipt в
`status/postgres-uploads/<dump-name>.json`. Она позволяет отличить отправленный дамп
от неудачной/неотправленной попытки даже после ротации remote-копии. Receipt удаляется
только вместе с одобренным старым локальным дампом. Прежний автоматический `prune` по
числу дней удалён, `--keep-existing` оставлен для совместимости.

Физический объём уменьшится после применения одобренного плана. Пока список не
одобрен, копии продолжают сохраняться; общий размер не является жёсткой квотой диска.
На будущем сервере после первых успешных копий нужно выполнить первый preview,
проверить предложенный список и только затем согласовать очистку.
