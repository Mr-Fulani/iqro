# Командная разработка

1. Клонируйте репозиторий и выполните [локальную настройку](docs/local-development.md).
   У каждого разработчика свои PostgreSQL, Redis, `.env` и `media/`.
2. Создавайте отдельную ветку для задачи. Изменения отправляйте через pull request.
3. Коммитьте код, миграции, тесты, документацию и lock-файлы. Не коммитьте секреты,
   БД, `.dev/`, `media/`, дампы, SDK, зависимости или собранные приложения.
4. Применённые миграции не изменяйте. Новая миграция должна работать и на пустой БД,
   и на существующих данных. UUID Корана используются прогрессом чтения и закладками.
5. Установка зависимостей: backend `uv sync --frozen --all-groups`, web `npm ci`,
   mobile `flutter pub get --enforce-lockfile`. Обновление версий — отдельное осознанное изменение.
6. Запускайте проверки затронутых компонентов: `make backend-check backend-test`,
   web `npm run lint && npm run typecheck && npm run test:e2e`, `make mobile-check`.
   Общие API/миграции проверяйте также в клиентах. CI проверяет backend с PostgreSQL.

После получения изменений `make up` применяет новые миграции и автоматически
подготавливает недостающие данные. Повторный запуск проверяет готовность и сохраняет
готовые каталоги. Для явного обновления источников: `make dev-data DEV_DATA_ARGS=--refresh`.
Существующие `.env` не перезаписываются: новые обязательные переменные добавляйте
в `.env.example` и документируйте.

Для остановки без удаления данных: `docker compose --env-file services/backend/.env stop`.
`reset-all` и `docker compose down -v` удаляют БД — это не часть обычного рабочего цикла.
Production/staging-инструменты предназначены для отдельно настроенных сред и не нужны
новому разработчику для локального запуска.
