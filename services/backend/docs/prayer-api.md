# Prayer times API and client contract

Модуль `prayer_times` предоставляет версионированный каталог методов расчёта и
stateless-расчёт расписания на один гражданский день. Он не хранит местоположение
пользователя и не управляет напоминаниями: профиль, локальные уведомления, push и азан
относятся к следующему этапу.

Результат расчёта является техническим расписанием по выбранному опубликованному методу,
а не самостоятельным религиозным заключением. Изменение параметров метода и добавление
региональных пресетов требуют проверки источника и содержательного/религиозного review.

## Роли клиентов

Целевой контракт различается по возможностям платформы:

- **Flutter — local-first.** Мобильный клиент получает и проверяет каталог методов,
  выполняет совместимую версию расчёта на устройстве и не передаёт координаты серверу в
  штатном сценарии. `POST /calculate` используется как fallback, пока локальный движок
  недоступен, не поддерживает опубликованную версию либо нуждается в контрольном расчёте.
  Реализация локального движка и уведомлений находится за пределами текущего backend-среза.
- **Next.js web — backend fallback.** После явного разрешения браузерной геолокации клиент
  отправляет координаты только в теле `POST /calculate`. Координаты нельзя помещать в URL,
  analytics events, server-rendered HTML или сохранять в `localStorage` по умолчанию.
- **Next.js Telegram Mini App — backend fallback.** Действуют те же правила приватности.
  Клиент не должен рассчитывать на фоновые таймеры или уведомления после закрытия WebView;
  гарантированный азан и локальные напоминания остаются обязанностью мобильного приложения.

Все клиенты должны хранить рядом с локальным расписанием `catalog_version`, ID и SHA-256
конфигурации, версию алгоритма, версию timezone database и пользовательские настройки.
Пересчёт обязателен при смене даты, координат/часового пояса, метода, мазхаба Асра,
high-latitude/polar правила, поправок или одной из опубликованных версий.

## Endpoints

Оба endpoint доступны без авторизации:

- `GET /api/v1/prayer/methods` — опубликованный каталог методов;
- `POST /api/v1/prayer/calculate` — расписание на один день.

Полный машинный контракт публикуется в OpenAPI по `/api/schema`.

### Каталог методов

`GET /api/v1/prayer/methods` возвращает только текущий опубликованный default release.
Ответ публично кешируется на 5 минут с `stale-while-revalidate=86400`, имеет слабый `ETag`
и поддерживает `If-None-Match`/`304`.

Начальный release `2026.1` содержит девять методов: Muslim World League, Egyptian,
Karachi, Umm al-Qura, Dubai, Moonsighting Committee, ISNA/North America, Kuwait и Qatar.
Для каждого элемента каталог возвращает:

- стабильный `code`, но ID конкретной версии конфигурации;
- названия и описания одновременно на AR/EN/RU;
- углы или фиксированный интервал Иша и method-level поправки;
- поддерживаемые/default high-latitude и polar правила;
- источник и его SHA-256;
- checksum всей нормализованной конфигурации.

Клиент не должен зашивать UUID или параметры метода в код. Он выбирает `id` из актуального
каталога, кеширует документ целиком и при расчёте передаёт его checksum. Это защищает от
незаметного использования конфигурации, отличной от той, которую видел пользователь.

Верхнеуровневые поля manifest:

```json
{
  "catalog_version": "2026.1",
  "configuration_schema_version": 1,
  "algorithm": {
    "id": "adhan-js-python-adapter",
    "version": "4.4.4-quran.1-adhanpy.1.0.5",
    "upstream": "a6f1a5c4a00105103f310ef18200b95f7184d2e7"
  },
  "timezone_database_version": "2026.3",
  "checksum_sha256": "...",
  "methods": []
}
```

Release публикуется атомарно и после публикации неизменяем. Исправления выпускаются новым
release и новыми configuration IDs/checksums. Допустимые состояния — `draft`, `published`
и `withdrawn`; одновременно существует ровно один опубликованный default release.
Withdrawn-конфигурация больше не рассчитывается (`410`).

### Расчёт одного дня

Пример запроса с синтетической точкой; в реальном приложении `method_config_id` и checksum
берутся из последнего ответа `/methods`:

```http
POST /api/v1/prayer/calculate
Content-Type: application/json

{
  "date": "2026-08-09",
  "timezone": "Etc/UTC",
  "location": {
    "latitude": "0.000000",
    "longitude": "0.000000"
  },
  "method_config_id": "b83b0ed4-5aa5-5ce3-b480-e0b9e2ad8850",
  "method_checksum_sha256": "<checksum из каталога>",
  "asr_method": "standard",
  "high_latitude_rule": "middle_of_night",
  "polar_resolution": "unresolved",
  "adjustments": {
    "fajr": 0,
    "sunrise": 0,
    "dhuhr": 0,
    "asr": 0,
    "maghrib": 0,
    "isha": 0
  }
}
```

Ограничения ввода:

- `date`: `1900-01-01`…`2100-12-31`;
- latitude: `-90`…`90`, longitude: `-180`…`180`, до 6 знаков после запятой;
- `timezone`: точный IANA identifier из закреплённого пакета `tzdata`;
- `asr_method`: `standard` или `hanafi`;
- каждая ручная поправка: целое число от `-120` до `120` минут;
- неизвестные поля, включая неизвестные вложенные поля, отклоняются.

Checksum формально опционален для совместимости, но production-клиент обязан передавать
его. Несовпадение даёт `409` и требует обновить каталог, а не повторять старый запрос.

Успешный ответ не повторяет координаты. Для каждого из `fajr`, `sunrise`, `dhuhr`, `asr`,
`maghrib`, `isha` возвращаются локальный ISO 8601 timestamp, UTC timestamp и
`utc_offset_seconds`. Кроме расписания ответ содержит точные версии метода/алгоритма/tzdb,
фактически применённые настройки, metadata fallback, предупреждения и
`next_recalculation_at` — начало следующего локального дня.

```json
{
  "date": "2026-08-09",
  "timezone": "Etc/UTC",
  "timezone_database_version": "2026.3",
  "method": {
    "id": "b83b0ed4-5aa5-5ce3-b480-e0b9e2ad8850",
    "code": "muslim-world-league",
    "catalog_version": "2026.1",
    "checksum_sha256": "..."
  },
  "algorithm": {
    "id": "adhan-js-python-adapter",
    "version": "4.4.4-quran.1-adhanpy.1.0.5",
    "upstream": "a6f1a5c4a00105103f310ef18200b95f7184d2e7"
  },
  "times": {
    "fajr": {
      "local": "2026-08-09T05:00:00+00:00",
      "utc": "2026-08-09T05:00:00Z",
      "utc_offset_seconds": 0
    }
  },
  "fallback": {
    "applied": false,
    "strategy": null,
    "reason": null,
    "reference_date": null
  },
  "warnings": [],
  "next_recalculation_at": {
    "local": "2026-08-10T00:00:00+00:00",
    "utc": "2026-08-10T00:00:00Z",
    "utc_offset_seconds": 0
  }
}
```

Фрагмент выше показывает форму ответа, а время `05:00` не является эталонным результатом.
Клиент должен использовать значения фактического ответа и не сверять их с примером.

## Время, DST и границы даты

Пара `date` + `timezone` задаёт локальный гражданский день, а координаты — положение для
астрономического расчёта. Backend не выводит timezone из координат и не проверяет, что они
географически соответствуют друг другу: эту пару формирует клиент либо выбранный
пользователем город.

Часовые пояса загружаются только из закреплённого Python wheel `tzdata`, а не из базы
операционной системы. Поэтому результат воспроизводим между контейнерами. Версия tzdb
возвращается в каталоге и каждом расчёте; локальный движок Flutter обязан использовать ту
же версию либо считать себя несовместимым. Offset вычисляется для каждого события
отдельно, что сохраняет корректность на переходах DST и при изменении исторических правил.

## High latitude и polar circle

High-latitude правило ограничивает Фаджр/Иша долей ночи от заката до следующего восхода:

- `middle_of_night` — половина ночи;
- `seventh_of_night` — одна седьмая;
- `twilight_angle` — доля `angle / 60`.

Для Moonsighting Committee применяется совместимая сезонная twilight-коррекция Adhan.
Аср рассчитывается с shadow length 1 для `standard` и 2 для `hanafi`.

Если на исходной широте нет полного восхода/заката, действует явно выбранная polar
стратегия:

- `unresolved` — не подменять данные и вернуть `422`;
- `aqrab_yaum` — найти ближайний день с полным solar day, проверяя до 183 дней в обе
  стороны; `fallback.reference_date` показывает использованный день;
- `aqrab_balad` — последовательно приближать расчётную широту к безопасной с шагом 0,5°;
  точная пользовательская или расчётная широта в ответ не возвращается.

При fallback ответ содержит `fallback.applied=true`, стратегию/причину и warning
`polar_resolution_applied`. При ненулевой пользовательской поправке добавляется warning
`manual_adjustments_applied`.

## Privacy и abuse protection

`POST /calculate` имеет жёсткий privacy contract:

- координаты существуют только в памяти процесса на время запроса;
- они не записываются в PostgreSQL, Redis, Celery, sessions, analytics или audit models;
- они не включаются в ответ, cache key, exception details и структурированные логи;
- response headers: `Cache-Control: private, no-store, max-age=0`, `Pragma: no-cache`,
  `Expires: 0`, `Vary: Authorization`;
- endpoint принимает location только в JSON body, никогда через query string.

Анонимный rate limit по умолчанию — `60/minute`. Для throttle в cache хранится только HMAC
от IP с отдельным секретом `QURAN_PRAYER_THROTTLE_HASH_KEY`; plaintext IP и координаты в
ключ не входят. Значение rate настраивается `QURAN_PRAYER_CALCULATE_RATE`.

Reverse proxy, APM и WAF в production также обязаны не записывать request body этого
endpoint. Разрешены только агрегированные метрики без location/IP: количество запросов,
коды ответа, latency, код метода и факт применения fallback. Сам backend не полагается на
client-side `no-store`: запрет кеширования устанавливается на каждом ответе, включая ошибки.

## Ошибки

Ошибки используют `application/problem+json` с `code`, безопасным `detail`, `request_id` и,
для validation errors, `field_errors`.

| HTTP | Типичная причина | Действие клиента |
| --- | --- | --- |
| `400` | неверный тип/диапазон, timezone или неизвестное поле | исправить запрос |
| `404` | ID отсутствует либо относится к draft | обновить каталог |
| `409` | checksum не совпал | обязательно перечитать `/methods` |
| `410` | release withdrawn или метод выключен | прекратить использование ID |
| `422` | неподдерживаемая версия движка/правило или unresolved polar day | выбрать поддерживаемую настройку; не угадывать время |
| `429` | превышен анонимный rate limit | учитывать `Retry-After` |
| `503` | отсутствует опубликованный default catalog | использовать проверенный локальный cache каталога |

Автоматически подменять `422` усреднённым временем, соседним городом или сохранённым
расписанием другого дня нельзя. Интерфейс должен явно показать, что расчёт недоступен, и
предложить пользователю выбрать разрешённую стратегию/город.

## Provenance и воспроизводимость

Первый release основан на MIT-licensed
[Adhan JS 4.4.4](https://github.com/batoulapps/adhan-js/tree/v4.4.4) и закреплённом upstream
commit `a6f1a5c4a00105103f310ef18200b95f7184d2e7`. Параметры методов взяты из versioned
[`CalculationMethod.js`](https://unpkg.com/adhan@4.4.4/lib/esm/CalculationMethod.js), их
исходный файл закреплён SHA-256 в каждой конфигурации. Описания методов сверяются с
[`METHODS.md`](https://github.com/batoulapps/adhan-js/blob/v4.4.4/METHODS.md); лицензия
upstream: [MIT](https://github.com/batoulapps/adhan-js/blob/v4.4.4/LICENSE).

Python package `adhanpy==1.0.5` используется только как адаптер астрономических примитивов.
Это более старый MIT-licensed port и не считается самостоятельным источником актуальных
методологических решений. Orchestration, high-latitude/polar поведение, округление,
seasonal twilight и исправление international date line закреплены в локальном движке и
сравниваются golden-тестами с Adhan JS 4.4.4. Обновлять `adhanpy`, Adhan или tzdata без
новой версии алгоритма/release и повторной дифференциальной проверки запрещено.

## Ограничения MVP

- Backend пока не хранит домашнюю локацию, prayer profile, настройки азана или расписание
  напоминаний и не отправляет push. Это следующий приоритетный модуль.
- Нет reverse geocoding и автоматического выбора метода по стране: пользователь/клиент
  выбирает опубликованный метод явно.
- Нет server-side bulk/calendar расчёта: endpoint намеренно рассчитывает ровно один день.
- В reference release Umm al-Qura использует фиксированные 90 минут после Магриба весь год.
  Автоматический особый интервал Рамадана ещё не включён: границы Рамадана и значение
  интервала требуют отдельного содержательного review. Клиент не должен молча считать 120
  минут официальной настройкой; временная ручная поправка Иша остаётся пользовательской и
  должна быть явно показана как `manual_adjustments_applied`.
- Каталог является проверяемым техническим baseline. Региональная точность и допустимость
  defaults должны быть подтверждены профильным content/religious review до широкого
  production rollout.
